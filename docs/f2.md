# F2 — Sedes, mapas y eventos

## Decisiones y comportamiento

- Las sedes tienen aforo de 1 a 100000 y zona America/Lima. La migración asigna 100 a las sedes demo existentes; el administrador puede ajustarlo. No se permite reducir el aforo por debajo de ningún evento existente.
- TenantAdmin crea/archiva sedes de su empresa. TenantAdmin y VenueManager administran mapas/eventos de sus sedes autorizadas. Caja, seguridad y barra solo consultan eventos dentro de sus asignaciones. Clientes y visitantes solo ven eventos publicados.
- Archivar una sede conserva relaciones y datos; sus rutas dejan de estar disponibles y se limpia el contexto de sesiones que la seleccionaron. Si tiene eventos publicados, se rechaza archivar. No hay borrado en cascada de datos de negocio.
- Una sede admite varias plantillas. Cada borrador tiene revisión y elementos relacionales; la geometría se guarda como JSONB con coordenadas normalizadas. Máximo 200 elementos por mapa. Los IDs son estables dentro de la plantilla.
- Guardar exige la revisión esperada. Un borrador cambiado por otra sesión responde 409; reabrir permite resolver el conflicto. La UI diferencia cambios sin guardar y bloquea publicar hasta guardar. Mover usa pointer events (ratón/táctil); el panel permite posición, tamaño y rotación mediante teclado.
- Publicar crea una versión inmutable con número, revisión de origen, nombre, fecha UTC y snapshot JSONB. Publicar dos veces la misma revisión devuelve la misma versión. El editor conserva el borrador y ofrece vistas de las versiones publicadas como solo lectura.
- Modos Exclusive, Capacity y Decoration explícitos. Escenario, barra, acceso y servicio siempre son decoración. La decoración tiene capacidad cero. Los recursos tienen capacidad humana positiva; publicar un mapa exige capacidad vendible de 1 al aforo de la sede.
- Un evento guarda fechas UTC y ventanas de operación; la web convierte explícitamente las entradas de America/Lima a UTC, y presenta fechas en Lima independientemente de la zona del navegador. Inicio < fin; ingreso cierra entre inicio y fin, con apertura anterior al cierre; canje abre/cierra dentro del evento. Se permiten eventos que terminan al día siguiente.
- El aforo del evento no supera el de la sede. Para publicar necesita una versión publicada de esa misma sede con capacidad suficiente; se vuelve a validar el aforo actual. Un borrador puede guardarse sin mapa, pero no publicarse.
- Publicar copia el mapa y el nombre/zona de la sede al evento. Crea recursos relacionales solo para elementos no decorativos: Exclusive asigna límite uno y conserva capacidad humana; Capacity asigna su capacidad como límite. Los futuros contadores held/sold y aforo global se implementarán en F3.
- Los eventos publicados quedan de solo lectura en F2. No hay edición estructural ni eliminación que pueda afectar futuros holds/ventas; modificaciones y cancelaciones comerciales requerirán su flujo posterior. El evento conserva el mapa aunque la plantilla o el nombre de la sede cambien.

## Transacciones y aislamiento

Todas las escrituras sobre una sede existente bloquean su fila con `SELECT … FOR UPDATE` dentro de una transacción PostgreSQL. Orden: sede, luego plantilla/evento y sus filas dependientes. Esto serializa cambios de aforo, guardado/publicación y archivo, sin locks en memoria. Unicidad por plantilla/revisión publicada, plantilla/número y evento/elemento refuerza los reintentos/concurrencia.

Plantillas, elementos, versiones, eventos y recursos llevan TenantId y VenueId. Las claves foráneas compuestas impiden asociar una versión o recurso con otra sede/empresa. Las consultas de personal incluyen ambos IDs; las rutas públicas derivan el alcance de eventos publicados. El catálogo público comparte intencionalmente datos publicados de todas las empresas; no expone borradores.

No se implementa idempotencia general de altas antes de F3. La publicación sí es repetible sin duplicar versiones ni recursos, gracias a la transacción y las restricciones. Las guardas de revisión impiden sobrescribir cambios concurrentes.

## API

Base de administración: `/api/v1/tenants/{tenantId}/venues/{venueId}`. Las políticas existentes y CSRF cubren todas las mutaciones.

| Método/ruta | Operación |
|---|---|
| GET/POST `/api/v1/tenants/{tenantId}/venues` | Listar sedes autorizadas / crear sede |
| GET/PUT/DELETE base | Consultar / actualizar nombre-aforo / archivar sede |
| GET/POST `base/layouts` | Listar / crear plantillas |
| GET/PUT `base/layouts/{templateId}` | Abrir / guardar borrador con expectedRevision |
| POST `base/layouts/{templateId}/publish` | Publicar revisión guardada |
| GET `base/versions` | Versiones publicadas de esta sede |
| GET/POST `base/events` | Listar / crear borrador de evento |
| GET/PUT/DELETE `base/events/{eventId}` | Consultar / actualizar / eliminar borrador |
| POST `base/events/{eventId}/publish` | Publicar y copiar recursos atómicamente |
| GET `/api/v1/public/events` | Hasta 100 eventos publicados, ordenados por inicio |
| GET `/api/v1/public/events/{eventId}` | Snapshot público con mapa y recursos |

Validación: 400; revisión/estado incompatible: 409; empresa/sede/ID ajeno: 404; rol insuficiente en empresa conocida: 403. DTOs tipados publicados en OpenAPI; el cliente TS se regenera con `npm run generate:api`. El contrato JSON exige números JSON para coordenadas/capacidades, evitando ambigüedad numérica.

Aplicada sobre la base F1 y sobre bases vacías de integración. El primer intento detectó el default cero de EF; se corrigió a 100 antes de aplicar y se preservaron todos los datos existentes.

Pruebas F2 en PostgreSQL real: ciclo borrador/publicación/snapshot, persistencia geométrica, independencia entre sedes/empresas, roles y CSRF, decoración no vendible, boxes exclusivos, límites y horarios, conflicto de revisiones concurrentes, publicaciones repetidas/concurrentes sin duplicación, CRUD y archivo, FK de versión de otra sede. Regresiones F0/F1 verificadas por su suite existente.

E2E desktop/móvil: crear sede, mover un box con ratón, ajustar tamaño/rotación, guardar, recargar, publicar mapa, crear/publicar evento nocturno, consultar lista, modificar/publicar segunda versión y comprobar que el evento conserva la primera.
